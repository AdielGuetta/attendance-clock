# הסבר להצגה (עד 10 דקות)

הזמנים בסוגריים הם הערכה. סה"כ כ-9.5 דקות. לפני ההצגה כדאי לפתוח את האפליקציה ואת GitHub (לשונית Actions).

---

## 1. מה בניתי (דקה)

- שעון נוכחות: עובד מחתים כניסה ויציאה ורואה את המשמרות שלו, ומנהל רואה דוח.
- ASP.NET Core 10, SQL Server ו-React.
- **הדרישה המרכזית:** השעה של כל החתמה מגיעה משירות זמן חיצוני של ציריך, ולא מהמחשב.
- הקושי האמיתי הוא לא המסכים, אלא המקרים שבהם דברים משתבשים: השירות נופל, העובד לוחץ פעמיים, שתי בקשות מגיעות יחד, הדף מתרענן, או שהשעון עובר לשעון קיץ.

## 2. הדגמה חיה (2.5 דקות)

1. מסך עובד: לוחצים **החתמת כניסה**. הטיימר מתחיל, ומופיעה הודעה עם השעה שהתקבלה מציריך.
2. **מרעננים את הדף (F5).** הטיימר ממשיך מאותה שעה, כי המצב נשמר בשרת ולא בדפדפן.
3. פותחים לשונית שנייה ומחתימים יציאה. הלשונית הראשונה מתעדכנת לבד.
4. מסך מנהל: היום, שבוע, פירוט ימים וייצוא CSV.

## 3. איך זה עובד מאחורי הכפתור (2 דקות)

אפשר להראות את `AttendanceRepository.PunchAsync`. הסדר הוא:

1. **בודקים אם הבקשה הזו כבר התקבלה.** לכל לחיצה יש מזהה ייחודי (`requestId`). אם הוא כבר שמור, מחזירים את התשובה המקורית בלי לרשום שוב.
2. **בדיקה מהירה:** אם יש כבר משמרת פתוחה, אין טעם לפנות לשירות הזמן.
3. **מקבלים שעה מהשירות החיצוני**, לפני שנועלים משהו במסד, כדי שבקשה איטית לרשת לא תתקע אחרים.
4. **נועלים את שורת העובד**, בודקים שוב ושומרים משמרת והחתמה באותה טרנזקציה.
5. **רשת ביטחון במסד:** אינדקס ייחודי שלא מאפשר שתי משמרות פתוחות לאותו עובד, גם אם יש באג בקוד.

## 4. מקרי הקצה (2.5 דקות)

| מקרה | הפתרון | איך מראים |
|------|--------|-----------|
| שירות הזמן נופל | ספק גיבוי (timeapi.io), ניסיון חוזר, ואם הכול נכשל: הודעה ברורה ושום דבר לא נשמר. אין גיבוי לשעון המחשב | `ExternalTimeServiceTests` |
| לחיצה כפולה | הכפתור ננעל, ואותו מזהה מחזיר את אותה קבלה | בדפדפן: שלוש לחיצות יצרו בקשה אחת |
| בקשות מתחרות | נעילת שורה ואינדקס ייחודי | בדיקה עם 5 בקשות במקביל: רק אחת מצליחה |
| רענון באמצע שליחה | המזהה נשמר בדפדפן, ואחרי רענון שואלים את השרת אם ההחתמה נשמרה | **באג שמצאתי ותיקנתי** (תיקון 8) |
| שעון קיץ וחורף | שומרים UTC. משך = הפרש אמיתי. גבולות יום = חצות בציריך. בשעה הכפולה בסתיו מכריעים לפי `dstActive` | משמרת לילה 22:00 עד 06:00 בליל המעבר = **9 שעות**, ולא 8 |

**את הבאג כדאי לספר:** בבדיקה בדפדפן לחצתי יציאה ורעננתי בזמן שהשירות היה איטי. המסך אמר "לא נשמר", אבל בשרת המשמרת כבר נסגרה, כי הבקשה המקורית עוד רצה.
התיקון: אחרי רענון ממשיכים לבדוק עוד 30 שניות לפני שקובעים שההחתמה לא נשמרה.

## 5. בדיקות ומה עוד פתוח (1 דקה)

- בדיקות יחידה ואינטגרציה מול SQL Server אמיתי, שרצות ב-GitHub Actions (להראות את הלשונית Actions).
- `verify-sql.ps1` בדק את המסד מקומית: 13 מתוך 13 עברו.
- 8 תרחישים בדפדפן. התיעוד נמצא ב-`docs/TESTING.md`, והתיקונים ב-`docs/FIXES.md`.
- **בכנות:** במחשב שלי Smart App Control חסם הרצה של קוד .NET מקומי, ולכן את השרת האמיתי הרצתי רק ב-CI. ההחלטה ומה נדרש כדי לסגור את הפער מתועדים.

## 6. החלטות ומגבלות (30 שניות)

- אין התחברות, וזו הדגמה מקומית שמוגבלת ל-localhost. לשימוש אמיתי צריך אימות והרשאות.
- SQL מפורש ולא EF, כדי שהנעילות יהיו גלויות.
- לעומת פרויקט הדוגמה: ספק גיבוי, דוח שמחלק משמרות לילה בין ימים כך שאפשר לסכום, וטיפול ברענון באמצע שליחה.

## 7. איך עבדתי עם Claude Code (30 שניות)

- התחלתי מתוכנית עבודה בקובץ (`.claude/plans/01-work-plan.md`) ועבדתי בשלבים, עם commit לכל שלב.
- `CLAUDE.md` מגדיר את הכללים שאסור לשבור, למשל "השעה רק משירות חיצוני" ו"לא מחזיקים טרנזקציה בזמן קריאה לרשת".
- כל באג נרשם ב-`docs/FIXES.md` עם הבדיקה שמכסה אותו.

### שאלות שכדאי להתכונן אליהן

- **למה לא לקחת את השעה מהשרת כשהשירות נופל?** הדרישה היא שעה חיצונית, ושעון שרת שמכוון לא נכון היה נרשם בשקט. עדיף להיכשל בגלוי ולאפשר ניסיון חוזר.
- **מה קורה אם שני שרתים רצים במקביל?** הנעילה היא במסד ולא בזיכרון, ולכן היא עובדת גם בין מופעים.
- **למה לשמור את מקור השעה?** לביקורת: אפשר לדעת מאיזה ספק הגיעה כל החתמה.
- **איך הייתם מוסיפים תיקוני מנהל?** טבלה נפרדת של תיקונים עם מי תיקן ולמה, בלי לשנות את ההחתמה המקורית.
